## 1. System Description and Categorization

Community Tech Aid (CTA) is a consumer AI tech-support application. Users create an account,
sign in, and receive AI-driven troubleshooting for scams, slow computers, popups, WordPress,
WiFi, TVs and soundbars, with an optional handoff to a real person by email. Paid access is
sold through Stripe. AI responses are generated by the Anthropic API from a server-side edge
function. The application is built and hosted on Lovable, with a backend running on Lovable
Cloud (a managed Supabase instance).

**Security categorization (owner-asserted, FIPS 199):** Confidentiality LOW, Integrity LOW,
Availability LOW. The system processes limited personal information (email address, source IP,
user-submitted chat and form content) for a commercial consumer service. It stores no federal
information, no cardholder data, no health records, and no government-classified data. The LOW
categorization is asserted by the owner and has not been through a formal, documented
categorization exercise under RA-2. See Known Gaps.

**Baseline scope:** This document addresses the base controls of the NIST 800-53 Rev 5 LOW
baseline that apply to this system, as enumerated by the owner. Relevant control enhancements
(for example multifactor authentication under IA-2) are discussed within their base control.
Program Management (PM) controls are organization-wide and are out of scope for this
system-level document.

## 2. Authorization Boundary

The authorization boundary is the CTA web application and the application data and functions
it runs, together with the managed platform components that host them. Because the backend is
a managed service the owner does not directly control, the boundary is described in three
layers: what the system builds and operates, what it inherits from providers, and what sits
outside as external interconnections.

## 4. Data Types and PII

The system collects and stores the following personal information: email address (account
identifier), source IP address (captured from `x-forwarded-for` for authentication events),
user chat content, and whatever users volunteer through the contact form
(`contact_messages`) and the demographics form (`demographics_submissions`). This data meets
the federal definition of personally identifiable information (PII). The impact level of the
PII is assessed as LOW.

The system does not store cardholder data. Stripe hosts checkout off-site and the system
records only plan status and expiration written back by `verify-paid-session`. The system
does not knowingly collect Social Security numbers, financial account numbers, health
information, or data from children.

## 5. Data Flows

1. **Web access.** User traffic reaches the Lovable-hosted frontend through the Cloudflare
   edge over TLS.
2. **Authentication.** The browser authenticates to Supabase Auth with email and password.
   The `log-auth-event` edge function writes a record to `auth_events` (event type and source
   IP from `x-forwarded-for`).
3. **Chat/AI.** The browser calls the `chat` edge function. For free-tier accounts the
   function checks `profiles.free_messages_used` against the 20-message lifetime cap before
   calling Anthropic. The Anthropic API key is held in edge-function secrets; the browser
   never calls Anthropic directly. The AI response returns through the edge function.
4. **Payment.** The browser is sent to Stripe hosted checkout. On completion,
   `verify-paid-session` matches the checkout to a Supabase account by email and writes
   `plan`, `plan_expires_at`, and `first_purchase_used`.
5. **Transactional email.** The system sends signup confirmation and magic-link recovery
   through Resend.
6. **Human handoff.** "Send to Human Support" forwards the conversation to the Proton support
   mailbox.
7. **Analytics.** The browser makes non-blocking calls to the `log-analytics` edge function
   (explicit CORS origin allowlist) which writes to first-party analytics tables. Cloudflare
   Analytics operates at the edge. No third-party analytics tooling is used.

## 6. Provider Responsibility Summary (Inherited Controls)

Many technical and physical controls are inherited from providers. Where a control below is
marked Inherited or Partially Implemented, the provider is named and the inherited portion is

  Supabase project directly, which constrains what the owner can configure or independently

- **Cloudflare:** edge TLS, DDoS protection, DNS integrity (DNSSEC where enabled), and network
  boundary protection at the edge.
- **Stripe:** PCI DSS compliant payment processing and cardholder data handling.
- **Anthropic:** security of the LLM inference service.
- **Resend:** transactional email delivery infrastructure.

## AC - Access Control

### AC-1 - Policy and Procedures
**Implementation Statement:** A written access control policy exists in the CTA policy manual (cta-policies.md, AC - Access Control Policy). It defines purpose and scope, assigns all access control roles to the single owner as the designated official, states management commitment, coordination with the authentication and edge providers, and compliance monitoring, and sets a review cadence of at least annually and following any significant system change. The policy documents the access control practices the system actually follows: authenticated and gated access, disabled anonymous sign-in, server-side validation of paid access, Row Level Security restricting users to their own rows, and administrative access limited to the owner.
**Evidence:** cta-policies.md (AC - Access Control Policy); Supabase Auth configuration; RLS policies; `ChatAccessGate`.
**Status:** Implemented.

### AC-2 - Account Management
**Implementation Statement:** End-user accounts are managed by Supabase Auth. Accounts are created through email/password signup, which fires a database trigger that creates the matching `profiles` row. A `user_roles` table holds role assignments separately from `profiles`. Administrative access to the platform (Lovable, Lovable Cloud backend view, Stripe, Cloudflare, Resend, Proton) belongs to the single owner. Two accounts currently exist in the user table, both belonging to the owner or a marketing collaborator. There is no documented account review cycle, and account disabling and removal rely on Supabase Auth and provider console actions rather than a written procedure.
**Evidence:** Supabase Auth; `profiles` table and signup trigger; `user_roles` table.
**Status:** Partially Implemented.

### AC-3 - Access Enforcement
**Implementation Statement:** Access to application data is enforced by Postgres Row Level Security, which restricts each authenticated user to their own rows. Access to paid functionality is enforced by `ChatAccessGate` on the `/chat` and `/triage` routes, which grants access for an active non-expired plan, an account under the free-message cap, or a legacy paid token that is validated server-side by `validatePaidTokenWithServer()`. The free-tier message cap is enforced server-side in the `chat` edge function before the Anthropic call. A prior version of the access gate enforced paid access from `localStorage` alone and was remediated (Finding 2026-01). Legacy beta access codes, which previously accepted any code of the correct length, have been retired entirely, and EXECUTE on the SECURITY DEFINER database functions has been revoked from the `public`, `anon`, and `authenticated` roles so that only the `service_role` can call them (Findings 2026-02 and 2026-05).
**Evidence:** RLS policies; `ChatAccessGate`; `validatePaidTokenWithServer()`; `supabase/functions/chat/index.ts`; retired `validate-beta`; SECURITY DEFINER EXECUTE lockdown.
**Status:** Implemented.

### AC-7 - Unsuccessful Logon Attempts
**Implementation Statement:** Failed logins are handled by Supabase Auth, which applies its own rate limiting to authentication endpoints. The application records `login_fail` events with source IP in `auth_events` through the `log-auth-event` edge function. The owner cannot configure a custom account lockout threshold or duration because Lovable Cloud does not expose those Supabase Auth settings; the lockout/throttling behavior is inherited from the platform.
**Evidence:** `log-auth-event` edge function; `auth_events` table; Supabase Auth rate limiting.
**Status:** Partially Implemented (throttling Inherited from Supabase; failure logging Implemented).

### AC-8 - System Use Notification
**Implementation Statement:** The login and signup screens present a system-use notice reading "Authorized use only. Activity on this system is logged," with a link to the Terms of Service. This is a client-side display notice, which is the appropriate form for a consumer web application. Public Terms of Service and Privacy Policy pages remain live.
**Evidence:** System-use notice on `Login.tsx` and `Signup.tsx` linking to `/terms`; `/terms`, `/privacy`.
**Status:** Implemented (client-side display notice).

### AC-14 - Permitted Actions Without Identification or Authentication
**Implementation Statement:** Unauthenticated users may view only public content: the homepage, `/pricing`, `/training`, `/privacy`, and `/terms`. All chat and troubleshooting functionality is gated behind authentication; anonymous sign-in is disabled. No privileged or data-modifying action is permitted without authentication.
**Evidence:** Public route set; `ChatAccessGate`; Supabase Auth with anonymous sign-in disabled.
**Status:** Implemented.

### AC-17 - Remote Access
**Implementation Statement:** The system is a public web application; all user and administrative access is remote by nature and occurs over TLS. Administrative access to the management planes (Lovable, Cloudflare, Stripe, Resend, Proton) is over each provider's authenticated HTTPS console. There is no separate corporate network, VPN, or private management interface to secure.
**Evidence:** Cloudflare edge TLS; provider consoles; multifactor authentication on all administrative provider accounts.
**Status:** Implemented (application), with edge TLS Inherited from Cloudflare.

### AC-18 - Wireless Access
**Implementation Statement:** The system operates no wireless networking. It is a cloud-hosted application with no owned facility, on-premises network, or wireless access points.
**Evidence:** Fully cloud-hosted architecture; no owned facility.
**Status:** Not Applicable (no organization-operated wireless).

### AC-19 - Access Control for Mobile Devices
**Implementation Statement:** The system does not issue or manage mobile devices and operates no mobile device management. End users reach the responsive web application from their own devices, which are outside the boundary and outside the owner's control.
**Evidence:** No owned or managed mobile device fleet.
**Status:** Not Applicable (no organization-managed mobile devices).

## 9. Findings and Remediation

### Finding 2026-01: Client-trusted paid access gate (remediated)

**Weakness.** An earlier version of the chat access gate used a hook, `usePaidAccess.ts`,
that returned an authorized result based solely on two `localStorage` values,
`cta_paid_access` and `cta_paid_access_expiry`, with no server-side verification. Because
`localStorage` is fully client-controlled, anyone could set those keys in browser devtools and
obtain unlimited paid access. This is a broken access control condition: a trust decision about
authorization was made entirely on the client.

**Detection.** The weakness was identified by the owner during a security review of the access
control path.

**Remediation.** The access decision was moved server-side. `ChatAccessGate` now routes the
legacy-token case through `validatePaidTokenWithServer()`, so genuine legacy tokens are
validated by the server while forged `localStorage` values no longer grant access. Active plan
and free-tier checks are likewise enforced server-side, with the free-tier cap checked in the
`chat` edge function before the Anthropic call. Remediation was completed the same day the
weakness was found.

**Control mapping.** AC-3 (Access Enforcement), SA-8 (Security and Privacy Engineering
Principles), SI-2 (Flaw Remediation), RA-7 (Risk Response).

**Residual note.** This was a self-identified, self-remediated finding. It is included because
a documented detect-and-correct cycle is stronger evidence of a working security practice than
an unblemished claim of full coverage.

---

### Remediation Log 2026-07-27

A deep security scan on 2026-07-27 surfaced additional findings, each remediated the same day.
This log records them and their control mappings.

**Finding 2026-02: Beta access code accepted any code of the correct length (Critical).** The
legacy beta access-code check validated only the length of the submitted code, so any string of
the right length granted access. Because access is now a free-tier-to-paid model, the beta path
was obsolete. Remediation retired it entirely: the `validate-beta` edge function and its config
were deleted and the `beta_session` token type was removed. Control mapping: AC-3, CM-7, SI-2.

**Finding 2026-03: Audit log entries forgeable by clients (Warning).** The `auth_events` table
accepted client-written rows, allowing forged audit entries. Remediation revoked INSERT from the
`anon` and `authenticated` roles, added a restrictive RLS insert-deny so only the `service_role`
writes, and changed `log-auth-event` to derive identity from the caller's JWT and the IP
server-side. Pre-authentication events accept only a syntactic email hint and are rate-limited to
20 per minute per IP. Control mapping: AU-9, SI-2.

**Finding 2026-04: Password length enforced client-side only (carried from the prior review).**
Remediation added the `secure-signup` edge function, which enforces the 12-character minimum and
a HIBP check server-side before the auth user is created. Residual: the raw `/auth/v1/signup`
endpoint is not covered by the length rule because Lovable Cloud exposes no "before user created"
hook; HIBP still applies there natively. Control mapping: IA-5.

**Finding 2026-05: SECURITY DEFINER functions executable by public roles (Warning).** EXECUTE on
the security-definer functions (`count_recent_login_fails`, the retention purge functions,
`prevent_spam_flooding`, `handle_new_user`, `set_updated_at`) was revoked from `public`, `anon`,
and `authenticated` and granted only to `service_role`. `has_role` is retained for
`authenticated` because RLS policies call it inline as the signed-in user. Control mapping: AC-3,
CM-6, least-privilege.

**Finding 2026-06: Missing rate limits and data-retention schedules (hardening).** Per-IP rate
limits were added to the magic-token endpoint (10 per minute) and confirmed on the contact
endpoint (3 per minute), each per edge-function instance. Daily `pg_cron` purges were added for
`chat_sessions`, `contact_messages`, and `demographics_submissions` (180 days). Non-blocking
Resend alerting was added for repeated login failures and edge-function errors. Control mapping:
SC-5, SI-12, SI-4, AU-5, AU-6.

**Finding 2026-07: Third-party dependency vulnerabilities (monitored).** A dependency scan found
13 known vulnerabilities. Upgrades and npm overrides reduced these to 6; the remaining 6 are

### 10.1 Confirmed gaps (control weaknesses stated honestly)

The family policy and procedure (-1) gaps are closed by the CTA policy manual (cta-policies.md).
The 2026-07-27 remediation (Section 9) closed several technical gaps previously listed here:
system-use notification (AC-8), data-retention scheduling (SI-12), audit-log tamper-resistance
(AU-9), the beta-code and SECURITY DEFINER findings, and server-side password enforcement (now a
residual rather than an open gap). The weaknesses below are what remain.

1. **IA-5 server-side password length (residual).** The 12-character minimum is now enforced
   server-side through the `secure-signup` edge function, but the raw `/auth/v1/signup` endpoint
   is not subject to it because Lovable Cloud exposes no "before user created" hook. HIBP
   breached-password checking applies on both paths.
2. **AU-6 scheduled review.** Automated alerting now fires on a defined login-failure pattern and
   on edge-function errors, but there is no scheduled, documented human review of audit records.
3. **CA-7 / SI-4 continuous monitoring.** Defined alert triggers now exist; there is still no
   monitoring strategy, metrics, SIEM, or dashboard beyond Cloudflare Analytics and the alerts.
4. **CP-2 / CP-4 / CP-10 contingency planning.** No written contingency plan and no tested
   recovery.
5. **CP-9 backups.** Backups are platform-provided only; the owner runs no independent backup
   and has not tested a restore.
6. **IR-4 / IR-8 incident response.** No defined incident handling process and no written
   incident response plan, though Section 9 now records several same-day remediations. The
   incident response policy exists (IR-1); the detailed plan and handling procedure do not.
7. **RA-2 / RA-3 risk assessment.** LOW categorization is asserted, not formally documented; no
   formal risk assessment exists.
8. **CM-2 / CM-4 configuration management.** No documented configuration baseline and no security
   impact analysis step for changes.
9. **Rate limiting is per-instance.** The application rate limits (magic-token, contact) run per
   edge-function instance, not as a distributed limiter; they blunt brute force but are not a WAF.
10. **Dependency residuals.** Six transitive dependency vulnerabilities remain with no patched
    upstream version available (recharts-bundled `lodash`; `@lovable.dev/mcp-js` build tooling),
    accepted as monitored residuals with low real-world exploitability.

    scanned, but there is no formal end-of-support calendar per component.

### 10.3 Structural constraint worth stating

Because Lovable Cloud is a managed Supabase instance the owner does not own (no service role
key, no direct database URL, no separate Supabase dashboard), several controls the owner would
otherwise implement or verify directly are constrained to what the Lovable editor exposes. This
constraint is not a failure of diligence; it is a property of the hosting model, and it is
disclosed here so that inherited and unverifiable controls are not mistaken for owner-operated
ones.
